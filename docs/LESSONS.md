# 教訓とこのコンペへの読み替え

前半は **Biohub でどう適用するか**、後半は**出典となった実測**（2026 年の ROGII Wellbore
Geology Prediction と PTCG で実際に踏んだもの。推測は含まない）。新しい実測がこのコンペで
出たら前半に追記し、出典は台帳の E 番号で示す。

## このコンペでの適用

**雑音床を最初に測る。** 評価単位は動画、指標はマイクロ平均の Jaccard。`6bba` の大きい動画
（GT 1,229 ノード）1 本が `44b6`（52 ノード）20 本分の重みを持つ。動画単位ブートストラップで
標準誤差を出し、台帳の前提表に書くまで「改善」と書かない。→ CHECKLIST Day 1

**公開 test 4 本はダミーで、LB はすべて hidden（train と重複なし・同規模 ≈200 本）。** この 4 本で
測ったローカル値は in-sample であり、LB の代理にならない（主催者回答 #716062、Overview 引用 #734237）。
hidden の系統比と public/private の内訳は未確認。**同一コードを 2 回提出**して LB のばらつき
（再実行のドロー）を測ること。

**公開 NB の表示スコアは再現しない。** 「clean 0.908」「LB 0.857」は名前に固定された数字。
`kaggle kernels pull` して自分で走らせ、未接触の動画で測り直す。「metric hack」を含む系譜
（負の t、体積外座標、クリップ跨ぎエッジ、人工ハブ）は外す。Kaggle が対処済みとされても、
hack に依存した構成は hidden で崩れる。

**事前学習済み資産は検証環境を選択的に壊す。** 公開 NB が添付する weights
（`pilkwang/biohub-tracking-support-pack-*` 等）は train の一部で学習済み。その weights の
重みを動かすノブ（検出閾値・ILP コスト）に対してだけ検証が誤る。学習 split を確認し、
未接触動画だけで測る。**対照アーム（逆方向のノブ）を必ず出す。**

**入力マウントのレイアウトは 2 種類。** `/kaggle/input/competitions/<slug>` と
`/kaggle/input/<slug>` を実行時に解決する（`notebooks/smoke_nn_baseline/main.py` は両対応）。
添付 dataset 側を `.exists()` でガードすると、欠落が**エラーを出さず静かに進む**ので、
必須資産は無ければ落とす。

**コード提出はランタイム超過で無得点になる。** hidden test の本数が不明なので、
1 動画あたりの秒数を台帳に記録し、実行時間上限（Rules ページで要確認・未記録）に対する余裕を見る。
提出後は `error_description` を確認する。

**ノード数はスコアに直接効く。** `adj = max(0, J · (1 − 0.1·(N_pred − N_true)/N_true))`。検出を増やす
施策は J の改善とペナルティ増の差し引きで見る。逆に N_pred < N_true なら係数は 1 を超える
（ボーナス。`max(0,·)` は下限クランプなので上限は無い。E0 実測: ratio −0.918 で J 0.0377 → adj 0.0412）。
打ち消すのは J の低下だけなので、両方向の腕を出す。

**in-sample 当てはめを採用根拠にしない。** 検出閾値・リンク距離・最小トラック長のような
ノブは 4 本の公開 test で容易に過学習する。固定 split（各系統 4 本）の未接触側で判断する。

**事前登録は負けを減らすだけ。** 勝つには検出器・リンカ・分裂検出という桁の違う軸が要る。

## 出典となった実測（ROGII / PTCG）

**指標の雑音床を最初に測る。** ROGII では public の帯 6.39〜6.70 の中で 0.01 単位の差を
1 か月追ったが、評価 52 件での標準誤差はおよそ 0.4〜1.2 だった。追っていた差は最も甘く
見積もっても標準誤差の 1/8 未満。この計算は初日にできた。

**in-sample の値は採用の根拠にしない。** 交差検証が魅力的な当てはめ値を 4 回覆した
（in-sample Δ → CV Δ。RMSE なので負が改善。−0.274 → +0.566 / −0.093 → +0.024 /
−0.337 → +1.399 / −0.15 → +0.035）。原因は誤差の集中で、最悪 5% の評価単位が二乗誤差の
52.5% を占めていた。

**完璧に見える証拠が揃っていても、未接触のドロー 1 点に負ける。** leave-one-site-out 6 ブロック
通過、変異試験でリーク差分ゼロ（199,746 行）、プラセボ対照つきで Δ −1.08 を示した施策が、
一度も触っていないデータで測り直すと −0.069 まで縮んだ。事前登録した棄却規則が提出を止めた。

**事前学習済み資産を含む検証環境は、一様にではなく選択的に壊れる。** フォーク元がマウントする
学習済みモデルが検証セットを記憶している場合、その資産の重みを動かすノブに対してだけ検証が
誤った評価を返す。同じ環境が、資産に触れないノブは正しく評価する。

**「検証環境が壊れている」という結論にも裏づけが要る。** ROGII では LB と検証環境が食い違い、
検証環境が誤りだと結論したが、private を見ると誤っていたのは public の側だった（検証環境の Δ と
private の相関 +0.72、public と private は −0.51。母集団を自提出 48 本に限ると −0.470）。測定器が 2 つあって食い違うとき、どちらが
正しいかは第 3 の証拠なしには決まらない。

**public スコアは測定値ではなくドローである。** 可視出力の SHA-256 が一致する 2 つのノートブックが、
非公開データでの再実行で 6.470 と 6.500 に分かれた。設定の比較はファミリー平均で行う。

**公開ノートブックのタイトルの数字は再現しない。** 4 件で食い違い、両方向に出た。作者は
スコアを名前に固定したまま更新を続ける。

**入力マウントのレイアウトが 2 種類あり、実行時まで分からない。** ハードコードするとコンペデータ側は
即死し、事前学習資産側は `.exists()` ガードのため静かに欠落する。後者で 7 回の実行を失った。

**フォーク元が SHA を固定した検証セルを持つことがある。** 緩めるのは例外送出だけにして、
構造的な検証は残す。

**提出の一部はランタイム超過で無得点になる**（実測 8%）。

**最終選択は Web UI からしか設定できない。** API の `SUBMISSION_GROUP_SELECTED` で読み戻して
検証するのが唯一の客観的な確認手段。

**提出枠は UTC 00:00 に回復し、採点には 10〜24 時間かかる。** 締切当日の枠は朝イチで使い切る。
